# Public repository publication boundary

The owner requires **hetaf234/2026-GP1-1 to remain Public** for graduation-project committee review. Publishing reviewed source is separate from enabling CI/CD, deploying infrastructure or granting mobile testers access. All current workflows remain .yml.disabled and all release flags remain false.

## Source and external runtime assets

frontend, backend, data, deployment, docs, security_tests and the inactive workflow templates are intended publication candidates. The two approved JSON hashes are in data/approved-hashes.json. deployment/source-map.json maps the lightweight runtime source to the original container layout; deployment/approved-runtime.json records all required runtime asset identities. Model binaries and the mandatory human-review registry/active references remain in the approved private Artifact Registry image pinned in deployment/policy.json. They are not available to anonymous GitHub readers. Authorized private-base access is required for a full Docker model-loading check; mocked unit/widget tests do not need the model weights or production secrets. Do not publish private records to make the image build public.

Android wrapper scripts/JAR are regenerated by the pinned Flutter SDK; local SDK paths, keystores and generated build outputs remain ignored. Firebase client configuration is intentionally included. Backend provider credentials are supplied only by the existing authorized runtime, not by Git. Public source publication grants no cloud access.

## Security review boundaries

Review tracked files, untracked non-ignored candidates and every reachable local Git-history blob. A secret scan is one check, not a guarantee. Do not upload ignored logs, .local, node_modules, build products, user backups, weights or signing material. Exact paths/sizes/hashes for publication are kept in the owner's local review evidence outside this repository.

Firebase client API keys identify the project and are designed for client distribution; they do not authorize Firebase Admin access. They must be restricted appropriately to Firebase services, while rules/IAM protect data. The final local repository review does not verify or change live API-key restrictions, quotas, App Check or Firebase settings. [Firebase API-key guidance](https://firebase.google.com/docs/projects/api-keys).

Project/app/repository IDs, registry paths, approved artifact digests and signing certificate fingerprints are identifiers, not private key material. No secret values or live user documents should appear here. Synthetic test fixtures are not production credentials. The standard existing debug-key password does not include the private signing key; debug-only internal distribution remains a separate decision.

## Known blocker to future automation activation

deployment/guard_reviewed_main.py checks that the repository is private. deployment/iam-plan.json likewise includes repository_visibility == private, and deployment/github-protection-plan.json retains a private-plan note. Those implementation/plan files were not changed by the documentation-only public review. Future deploy/distribution attempts with the current gates will fail for this Public repository. This does not block publishing source while all workflows stay disabled. Do not change visibility, remove review gates or grant IAM merely to bypass the failure.

A separately approved implementation must support Public while preserving exact numeric repository/owner identity, main push and workflow-ref restrictions, review of the current PR head, restricted identities and protected upload/deploy environments. Public fork PRs must have no cloud identity, signing secret or privileged pull_request_target execution; review both CI and publisher trust boundaries before activation. [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).

Misbar CI is not yet active, so branch protection must not claim it has already passed. No Cloud Build trigger, new IAM identity, signing secret, upload group or USB-free backend path was activated by the local preparation. APP_DISTRIBUTION.md and BACKEND_CONNECTIVITY.md describe the remaining separate approvals.
